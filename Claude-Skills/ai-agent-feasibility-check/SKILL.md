# AIエージェント実現性診断

## 目的

「AIエージェントを作りたい」という案件に対して、現状をヒアリングし、実現性を診断票として出力する。単なる要件の聞き取りではなく、生成AIの技術的根拠に立脚して、失敗リスクの検知・フォロー策の提示・実現度の指標化までを行う。使用者本人（思考整理・抜け漏れ防止のための壁打ち相手）を想定する。

## 動作の流れ

1. 案件の輪郭を1問で掴む
2. 7つの診断項目を3グループに分け、対話的にヒアリングする（グループ単位で区切って聞く）
3. 回答が出揃ったら診断票（Markdown）を生成する

ヒアリングは要点を突いてテンポよく進める。依頼者向けの冗長な聞き方はしない。一問ずつ答える過程で「ここが握れていない」と気づかせること自体が狙いなので、グループ単位で区切り、回答に応じて深掘りする。

## ヒアリングの質問フロー

### 導入：案件の輪郭

- そのAIエージェントに、何を入力したら、何を出力させたいか（入力と出力を一文で）

ここでタスクの全体像を掴み、以降の質問の当て方を調整する。

### グループA：タスクの性質系

- そのタスクは、入力から必要な情報を「そのまま抜き出す」のに近いか、それとも「読み取って解釈し、書き換える・補う」のに近いか（→項目4）
- 処理の工程のうち、AIに任せたい範囲と人間が担う範囲の線引きはついているか（→項目5）

### グループB：データが足りない系

- 完成した出力の「お手本」になるサンプルは何件くらい手に入るか。ゼロか（→項目1）
- 実際に処理させる入力データは事前に何件か見られるか。機密などで見られない場合、構造だけでも分かるか（→項目2）
- 今その出力を人間が作っているとして、その人の判断ロジックを聞ける立場にあるか（→項目3）

### グループC：期待値・合意系

- この成果物に、品質保証や「必ず正しい」ことを期待されているか。許容される誤りの幅は握れているか（→項目6）
- 何をもって「成功・完成」とするかの合意や基準はあるか（→項目7）

各質問は「はい/いいえ」で終わらせず、程度（何件か、どこまで握れているか）を引き出す。機密で答えられない場合の逃げ道（構造だけ、判定例だけ）を織り込む。

## 根拠ライブラリ（7項目）

各項目は「失敗要因 ⇄ 技術的根拠 ⇄ フォロー策」で構成される。技術的根拠は4層（原理／法則／制限／性質）で整理する。

### 技術的根拠の語彙（4層）

- 原理：最も根源的な成り立ち。確率的生成（同じ入力でも出力が揺れる／正解ではなく尤もらしさを出す）、暗黙知の非転移性（語れる以上のことを知っている＝言語化されない判断はサンプルから逆算しきれない）
- 法則：例外なく成り立つ規則性。GIGO（入力の質が出力の質を規定する）、スケーリング則の裏返し（ユーザー側で上げられるのは性能でなく文脈とデータ）
- 制限：系として越えられない境界。グラウンディング不在（正解・実データに接地しないと検証できない）、コンテキストウィンドウの有限性、知識カットオフ
- 性質：傾向としての振る舞い。ハルシネーション、確率的非決定性、コンテキスト依存性、タスク類型による難易度差（抽出は安定／解釈・補完・翻訳は不安定）

### グループ1：データが足りない系

**項目1：正解サンプルがない**
- 一般化：期待する出力の正解例が入手できない
- 技術的根拠：グラウンディング不在（制限）／確率的生成（原理）
- フォロー策：完成品サンプルを最低1〜2件確保／無理なら良し悪しの判断基準だけでも言語化してもらう／本当にゼロなら品質保証はできない前提で握る

**項目2：入力サンプルがない**
- 一般化：実際に処理させる入力データが事前に得られない
- 技術的根拠：GIGO（法則）／コンテキスト依存性（性質）
- フォロー策：代表的な入力を数件もらう／機密なら構造だけ（項目・粒度・ばらつき）を共有してもらう／項目1とセットで揃える

**項目3：ロジックを持つ人に接触できない**
- 一般化：出力を生み出している人間の判断ロジックにアクセスできない
- 技術的根拠：暗黙知の非転移性（原理／性質）
- フォロー策：担当者へ一度でいいのでヒアリング機会をもらう／個人に当たれないなら部署・チーム単位で判断基準を集める
- 注記：埋まらない場合のリスクは特に重い（他の材料が揃っても品質の天井が決まる）

### グループ2：タスクの性質系

**項目4：タスクが「解釈・翻訳」型である**
- 一般化：タスクが単純な抽出でなく、解釈・補完・翻訳を伴う
- 技術的根拠：タスク類型による難易度差（性質）
- フォロー策：タスクを工程分解して抽出できる部分と解釈が要る部分を切り分ける／解釈部分はルール化できないか検討する
- 注記：フォローというより難易度の見積もりに効く

**項目5：スコープの曖昧さ**
- 一般化：どこまでをAIに任せ、どこからを人間がやるかの線引きがない
- 技術的根拠：タスク類型による難易度差（性質）／確率的生成（原理）
- フォロー策：工程を分解して「AI担当／人間担当／レビュー」を明示的に割り振る／不確実性の高い工程は人間側に寄せる
- 注記：項目4と組み合わせるとタスク設計の健全性を診る軸になる

### グループ3：期待値・合意系

**項目6：前例・実績がない／品質保証を求められる**
- 一般化：横展開できる既存の型がなく、かつ成果物の品質保証を期待されている
- 技術的根拠：確率的生成・非決定性（原理／性質）
- フォロー策：品質保証ではなく「許容できる誤り率」と「人間レビューの工程」を前提に握る／小さく試して実績を作ってから広げる

**項目7：評価基準の不在**
- 一般化：何をもって成功とするかの合意がない（サンプル以前に測る物差しの定義がない）
- 技術的根拠：グラウンディング不在（制限）
- フォロー策：合格条件を具体的な観点（必須項目の網羅／表現の正確さ／許容できる誤りの種類）に分解して合意する／定量化が難しければ「この出力ならOK/NG」の判定例を数件もらう

## リスク評価と実現度スコア

### 三段階評価

各項目を回答の埋まり具合で三段階評価する。
- リスク低：十分に埋まっている（例：正解サンプルが複数件ある）
- リスク中：部分的に埋まっている（例：判断基準だけある）
- リスク高：埋まっていない（例：何もない）

### 実現度スコア

各項目の評価に重みを掛けて集約し、実現度スコア（目安）として出す。

重みの初期値（序列）：
- 最重量：項目3（人間ロジックへの接触）
- 重い：項目1（正解サンプル）、項目4（タスクが解釈・翻訳型）
- 中程度：項目2（入力サンプル）、項目7（評価基準）
- 握り直しで対処しやすい：項目6（品質保証の期待）、項目5（スコープ）

重要：この重みは初期値であり、固定値ではない。診断のたびにスコアを出しつつ、重み付けが一つの想定に過ぎないことを票に添える。案件の性質から見て重みの序列が実態と合わないと判断したら、その旨を指摘する。スコアはあくまで目安であり、確率的生成を根拠に置くスキルとして、自身の出す指標を過信させない。

## 診断票のレイアウト（出力形式）

Markdownで以下の順に出力する。上から「結論ゾーン → 詳細ゾーン → 留保ゾーン」と読める構成。

1. **ヘッダー**：案件名と、何を入力して何を出力するタスクなのかを一文で
2. **実現度スコア**：数値（目安である旨を併記）＋重い項目の状態
3. **最優先アクション**：今いちばんのボトルネックになっている項目と、次に打つべき一手を1〜2行で（票内で最も目立たせる）
4. **7項目の診断一覧**：3グループで区切り、各項目に「評価（三段階）／検知したアラート／技術的根拠／フォロー策」を並べる
5. **重み付けに関する注記**：スコア算出に使った重みが初期値で見直し可能であること、案件の性質と合わない場合の指摘

## 対外出力モード（HTML）

診断結果を対外的に提示するための、視覚化された単一ファイル HTML を出力するモード。「対外用に出力」「HTML で出して」「診断票を見せる形にして」などの依頼で起動する。あくまで確定済みの診断結果を出力するだけのモードで、診断のやり直しはしない。

### 方針

- 文体は内部用の辛口表現のまま出力する（中立化しない）。率直な物言いを残す。
- 出力は単一ファイル HTML で完全に自己完結させる。チャートは CDN を使わず自前の SVG で描く（回線が不安定な場でも確実に表示するため）。
- テンプレートは、このスキルフォルダに同梱した `diagnosis_report_sample.html`（SKILL.md と同じ階層、相対パスで参照する）。これを複製し、データ（案件名・タスク概要・スコア・各項目の評価とアラート・根拠・フォロー策・レーダーの `items` 配列）を差し替えて生成する。
- テンプレートにはサンプル案件（要望書→仕様書）のデータが入っている。生成時は全項目を必ず新案件の内容で上書きすること。書きぶり・トーンの見本としてサンプル文は参照してよいが、データとしては残さない。
- 仕上げに、前案件の語（「仕様書」「要望書」「Copilot」など）が新案件と無関係に残っていないかを照合してから出力する。`{{ }}` のような空欄も残さない。

### レーダーチャート

- 7 項目を 7 軸として配置し、各軸に「実現度」をプロットする。
- 実現度はリスク評価を反転して数値化：リスク低 = 3／リスク中 = 2／リスク高 = 1。
- 塗りつぶし面積が小さいほど準備不足が一目で伝わる。歪に縮んだ多角形は「材料が揃っていない」ことを視覚的に示す。
- データは HTML 末尾スクリプトの `items` 配列（label と value）を差し替えるだけで反映される。

### レイアウト

Markdown 版の診断票と同じ並び（ヘッダー → 実現度スコア＋レーダー → 最優先アクション → 7 項目一覧 → 重み付け注記）を、スタイルを当てて配置する。リスク高／中／低はバッジで色分けする（高 = 錆色、中 = 琥珀、低 = 若草）。

## 共通ルール

- 出力はMarkdown形式（装飾は不要、構造化された一覧で十分）
- 絵文字は使用しない
- 無駄な前置きは省く
- リスクとフォローは必ず技術的根拠（法則・制限・性質）に紐づけて示し、対策の有効性を高める
- アラートは各項目で出しつつ、最終的に実現度として集約する
